# 验收标准闸门（qa 预先签署）

**一句话**：验收标准由 **qa 先写、qa 先签**；pm 拆卡时只转抄 qa 的结论，不代签。两道检查——
**建卡时**验「有没有签」，**收口时**验「谁来关」。

模板侧的写法见 [`docs/card-template.md`](card-template.md) 第 7 块；本文只写口径、边界与自查
命令。内核侧两张卡：建卡闸门 `t_9cfd9d8d`、完成闸门 `t_90468e1d`（文案 / rc 以其实际合入的
实跑为准）；返工归因口径见 R14。

## 1. 为什么

返工归因（R14）把每次打回标成 `spec` / `impl` / `env` 三类。实测（2026-10-31 复核截面，
板上 `changes_requested` 事件的归因分布）：**spec 7 条 / impl 4 条**，另有**若干**历史事件
未标因（`UNTAGGED`，按 R14 不参与统计）。也就是说，那一截面里 **7/11 的已归因返工是卡面
写错**（判据自相矛盾、卡内数字与 fixture 冲突、验收标准漏写），不是实现走样。

上述计数是**截面值，随板增长**（板上每多一次打回就变），引用前先自查 —— R14 ⑤ 的唯一校验
命令，输出第一段即分因占比；另有 `UNTAGGED` 若干条单列，不折进 `spec` / `impl`：

```
$ sqlite3 -header -column ~/.hermes/kanban/boards/devteam/kanban.db \
    < ~/.hermes/profiles/ops/workspace/rework_audit.sql
```

等价读法：取 `task_events` 里 `kind='changes_requested'` 的行，`payload.reason` 首行的
`REWORK-CAUSE:` 值即归因；无此行的记 `UNTAGGED`。

结论：问题不在验收轮次太少，而在**验收标准出场太晚**——派卡时只有一句「完成目标」，跑完
才第一次把判据说清，返工必然跑在实现者头上。修法是把验收标准前置：**派卡前写清判据，
并由 qa 签名**，卡面错了在开跑前就被拦住。

## 2. 建卡闸门（建卡时就拦）

- **适用范围**：`assignee=engineer` 的实现卡。其余 assignee（pm / qa / repo / ops，以及老板
  手写的需求卡）**不受约束** —— 需求卡不因为漏了这一段被拦。
- **判据两条，缺一条即拒**：
  1. 正文里存在**单独一行、逐字** `## 验收标准`（顶格、不带编号）；
  2. 该段的**第一条非空行**整行恰为 `QA-SPEC: qa`（顶格、大小写敏感、冒号后是半角空格、
     行内不许别的内容）。段的结束 = 下一个以 `## ` 开头的行或正文结尾。
- **拒绝行为**（随卡 `t_9cfd9d8d` 落地，**以该卡实跑为准**）：`hermes kanban create` 返回
  **rc=2**、stderr 恰一行、**卡不落库**；`kanban_create` 工具返回 `{"error": …}`，同样不落库。
  「缺段」与「缺签署」是两条分开的文案，不复用一句。
- **不提供的口子**：没有关闭开关、不截断正文、不自动补段、不事后转正。要放宽范围只能改内核
  里那个「必须签署的 assignee」元组（唯一一处）。
- **闸门未合入前的现状**：建卡暂时不会拦。模板与本文已是要求；合入前照抄第 7 块，别等闸门。

### 自查命令（贴在要检查的卡正文上）

卡正文先落到文件 `body.md`（或直接从 `kanban_show` 里取 `body`），两条各返回一行命中即合规：

```
$ grep -n '^## 验收标准$' body.md
$ grep -n '^QA-SPEC: qa$' body.md
```

连「签署行是否段内第一条非空行」一起看（`-A2` 取段标题后两行，第二行必须是签署行）：

```
$ grep -A2 '^## 验收标准$' body.md
```

任一条 rc=1（无命中）就是缺段或缺签署 —— 建卡闸门合入后会被拒成 rc=2。

## 3. 完成闸门（卡只能由 qa 收口）

- **判据**：正文带顶格整行 `QA-SPEC: qa` 的卡，**只有 qa 的 run 能 `complete`**。
- **pm 的验收 run 被拒**：状态零变更、不发完成事件。出路三条，按场景选：
  - `kanban_request_changes(reason=…)` —— 实现没达标，打回重做；
  - `kanban_request_review(reviewer="qa")` —— 实现达标，转给 qa 收口；
  - `kanban_comment(body=…)` —— 只留话，不改状态。
- **无 active run 的 CLI 手工 `complete` 同样被拒**。`--force` 是运维逃逸口，不是常规路径：
  放行会写一条审计事件（记录 profile / run_id / 时间），事后可查，不许静默放行。
- **行为细节**（工具侧 `tool_error` 文案、CLI 的 rc=2 与「stderr 恰一行、零 traceback」）随卡
  `t_90468e1d` 落地，**以该卡实跑为准**。
- **不受影响**：`kanban_request_changes` / `kanban_comment` / `kanban_request_review` 三条
  路径的行为不变 —— pm 照样能打回、能留言、能转签。

## 4. 存量不追溯

- 只约束**新建**卡。旧卡不改正文、不补签、不因缺这一段被回头判不通过。
- 已 `done` 的卡不重判；在途卡不中断。
- 想给旧卡换口径：**新开一张卡**，不改旧卡 —— 历史保持可追溯。
